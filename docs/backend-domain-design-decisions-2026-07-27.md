- 대상 브랜치: `demo/backend-completion-20260726`

## 1. 문서 목적

이 문서는 현재 백엔드 코드가 각 도메인의 핵심 문제를 어떤 방식으로 해결하고 있는지 설명한다. 단순한 클래스 목록이 아니라 다음 질문에 답하는 것을 목적으로 한다.

1. 각 도메인이 책임지는 업무는 무엇인가?
2. 중요한 흐름과 데이터는 어떤 방식으로 구현했는가?
3. 왜 현재 방식을 선택했는가?
4. 선택할 수 있었던 다른 방식에는 무엇이 있으며, 각각 어떤 장단점이 있는가?
5. 현재 구현에서 주의할 점과 추후 구현으로 남겨야 할 범위는 무엇인가?

문서에서 `현재 구현`은 실제 코드에서 확인된 동작을 뜻한다. `대안`은 비교를 위한 설계안이며 현재 구현된 기능이 아니다. `추후 구현`은 코드에 TODO가 있거나 현재 구조만으로 운영 수준의 완결성을 보장하기 어려운 항목이다.

## 2. 전체 아키텍처와 공통 설계 원칙

### 2.1 모듈 분리

백엔드는 다음 책임을 중심으로 멀티 모듈로 나뉜다.

| 모듈 | 주된 책임 |
|---|---|
| `gm-api` | HTTP API, 인증 필터, WebSocket 설정, 요청 검증, 예외 응답 |
| `gm-core` | 도메인 모델, 유스케이스 서비스, 포트 인터페이스, 정책 |
| `gm-storage-db` | JPA·QueryDSL 기반 영속성 어댑터 |
| `gm-storage-redis` | 임시 인증 정보, 투표 상태, 분산 데이터 저장 |
| `gm-client` | 네이버 OAuth, Kakao 장소 검색, OpenAI 연동 |
| `gm-mq` | 비동기 이벤트 발행·소비와 메시지 계약 |

핵심 방향은 `gm-core`가 JPA, Redis, 외부 HTTP 클라이언트 같은 구체 기술을 직접 알지 않도록 하는 것이다. 코어에는 `Repository`와 외부 연동 `Port`를 두고, 실제 구현은 각 인프라 모듈이 제공한다.

이렇게 한 이유는 다음과 같다.

- 비즈니스 규칙과 저장 기술을 분리해 정책 변경의 영향 범위를 줄인다.
- 추천, 투표, 식당 검색 같은 유스케이스를 인프라 세부 사항 없이 테스트할 수 있다.
- DB와 Redis처럼 수명이 다른 데이터를 각각 적합한 저장소에 둘 수 있다.
- 외부 API 공급자를 교체할 때 코어 로직을 최대한 유지할 수 있다.

### 2.2 공통 데이터와 응답 정책

- 주요 엔티티 식별자는 UUID 계열을 사용한다.
- 생성·수정 시각은 공통 기반 엔티티에서 관리한다.
- HTTP 응답은 공통 응답 봉투와 전역 예외 처리기를 사용해 성공·실패 형식을 통일한다.
- 권한 검증은 컨트롤러에만 두지 않고 실제 상태를 변경하는 서비스에서도 수행한다.
- 여러 쓰기 작업이 하나의 업무 결과를 구성하면 트랜잭션으로 묶는다.
- 외부 메시지 발행이나 Redis 정리처럼 DB 커밋 이후 실행돼야 하는 작업은 가능한 한 커밋 이후 처리한다.

### 2.3 고려할 수 있었던 다른 구조

| 대안 | 장점 | 단점 | 현재 구조를 선택한 이유 |
|---|---|---|---|
| 단일 모듈 계층형 구조 | 초기 개발과 탐색이 빠름 | 도메인과 인프라 결합이 커지고 변경 영향 범위가 넓어짐 | 추천·투표·외부 연동의 복잡도를 경계별로 관리할 필요가 있었음 |
| 도메인별 마이크로서비스 | 독립 배포와 확장이 쉬움 | 분산 트랜잭션, 운영, 관측 비용이 큼 | 현재 규모에서는 모듈러 모놀리스가 개발 속도와 경계 관리의 균형이 좋음 |
| 서비스에서 JPA·Redis 직접 사용 | 코드가 짧고 직관적일 수 있음 | 테스트와 기술 교체가 어려움 | 핵심 정책을 저장 기술과 분리하는 편이 장기 유지보수에 유리함 |

### 2.4 공통 영역의 추후 과제

- DB 변경과 MQ 발행의 원자성을 보장하는 트랜잭셔널 아웃박스는 현재 완성된 구조로 확인되지 않는다.
- 분산 추적, 메시지 처리 지연, Redis 키 만료 같은 운영 지표를 일관되게 관측하는 체계가 필요하다.
- 전체 통합 테스트는 현재 성공 상태가 아니다. 문서 작성 직전 확인된 전체 테스트에서는 264개 중 34개가 실패했으며, 다수는 그룹 소유자 외래 키를 만족하지 못하는 테스트 픽스처 문제였다. 따라서 현재 구현을 “전체 회귀 테스트 통과” 상태로 해석하면 안 된다.

## 3. 인증 도메인

### 3.1 책임

인증 도메인은 네이버 OAuth 로그인, 자체 액세스·리프레시 토큰 발급, 로그인 결과 전달, 토큰 재발급, 로그아웃을 책임진다.

### 3.2 중요한 구현

로그인 완료 후 토큰을 브라우저 리다이렉트 URL에 직접 노출하지 않는다. 대신 다음 흐름을 사용한다.

```text
네이버 OAuth 성공
→ 서버가 Refresh Token을 HttpOnly 쿠키로 설정
→ Redis에 일회용 Login Exchange Code 저장
→ 프런트엔드로 Exchange Code만 전달
→ 프런트엔드가 /api/auth/token 호출
→ 서버가 코드를 원자적으로 소비하고 쿠키의 Refresh Token과 사용자를 대조
→ Access Token을 응답 본문으로 발급
```

로그아웃 시에는 남은 유효 시간 동안 액세스 토큰을 Redis 블랙리스트에 등록하고, 리프레시 토큰과 관련 로그인 상태를 삭제하며 쿠키도 만료시킨다. API 인증은 상태를 서버 세션에 두지 않는 JWT 필터 방식으로 처리한다.

### 3.3 이 방식을 선택한 이유

- 액세스·리프레시 토큰을 OAuth 리다이렉트 URL에 넣으면 브라우저 기록, 프록시 로그, 분석 도구, Referer 등에 노출될 수 있다.
- 일회용 교환 코드는 짧게 유지할 수 있고, 한 번 사용하면 다시 쓸 수 없어 탈취 시 재사용 범위를 제한한다.
- Refresh Token을 HttpOnly 쿠키에 두면 자바스크립트에서 직접 읽을 수 없어 일반적인 XSS 상황에서 탈취 가능성을 낮춘다.
- Access Token을 Authorization 헤더로 전달하면 API 인증 흐름이 명시적이며, 쿠키 기반 인증에서 추가로 고려해야 하는 CSRF 범위를 줄일 수 있다.
- 로그아웃 블랙리스트는 서명된 JWT가 만료 전까지 자체적으로 유효하다는 단점을 보완한다.

### 3.4 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| 서버 세션 | 즉시 세션 폐기와 권한 변경 반영이 쉬움 | 세션 저장소 의존성과 수평 확장 관리가 필요함 |
| 토큰을 리다이렉트 URL에 포함 | 구현이 단순함 | URL을 통한 토큰 유출 위험이 큼 |
| Access·Refresh Token 모두 쿠키 사용 | 프런트 토큰 관리가 단순함 | CSRF 방어 정책을 더 엄격하게 설계해야 함 |
| Refresh Token Rotation | 탈취된 리프레시 토큰 재사용 탐지가 가능함 | 토큰 패밀리와 재사용 탐지 상태 관리가 복잡해짐 |

현재 구현은 프런트 연동 단순성과 토큰 노출 방지 사이의 균형을 택했다. 다만 운영 보안 수준을 높일 때는 Refresh Token Rotation이 우선 검토 대상이다.

### 3.5 추후 구현 및 주의점

- Refresh Token Rotation과 재사용 탐지는 추후 구현 대상이다.
- Access Token 블랙리스트는 Redis 가용성의 영향을 받으므로 장애 시 인증 정책을 명확히 해야 한다.
- CORS 허용 출처는 운영 환경별로 최소 범위만 허용해야 한다.

## 4. 사용자 및 음식 설정 도메인

### 4.1 책임

사용자 도메인은 OAuth 사용자 생성, 온보딩 상태 전환, 약관 동의, 알레르기·선호 메뉴·비선호 메뉴·선호 카테고리·비선호 카테고리·자유 입력 설정을 관리한다.

### 4.2 중요한 구현

OAuth 사용자는 `provider`와 `providerId`로 조회하며, 존재하지 않으면 `ONBOARDING` 상태로 생성한다. 온보딩을 완료할 때는 다음 검증과 변경을 하나의 트랜잭션으로 처리한다.

1. 필수 약관 동의를 확인한다.
2. 선호와 비선호 목록이 겹치지 않는지 확인한다.
3. 요청에 포함된 메뉴·카테고리·알레르기 ID가 마스터 데이터에 존재하는지 검증한다.
4. 기존 관계 데이터를 삭제한다.
5. 요청된 관계 데이터를 다시 저장한다.
6. 사용자 상태를 `ACTIVE`로 전환한다.

음식 설정은 관계 테이블의 구조화된 ID와 사용자가 직접 작성한 자유 텍스트를 함께 저장한다. AI 추출 결과를 바로 저장하기보다 사용자가 확인할 수 있는 분석 결과로 돌려주는 흐름을 둔다.

### 4.3 이 방식을 선택한 이유

- 구조화된 ID는 추천 필터링과 통계에 안정적으로 사용할 수 있다.
- 자유 텍스트는 마스터 데이터가 아직 표현하지 못하는 취향과 알레르기를 보완한다.
- 전체 설정 갱신을 삭제 후 재삽입으로 처리하면 최종 상태가 요청 본문과 정확히 일치하며, 관계별 추가·삭제 분기 로직을 단순화할 수 있다.
- 마스터 ID를 먼저 검증하면 존재하지 않는 설정이나 참조 무결성 오류를 업무 오류로 명확히 돌려줄 수 있다.
- AI 결과를 사용자 확인 없이 저장하지 않음으로써 잘못된 추출이 안전 필터나 추천 품질에 바로 반영되는 것을 막는다.

### 4.4 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| PATCH 기반 증분 수정 | 변경량이 적고 부분 수정에 적합 | 추가·삭제·충돌 규칙과 멱등성 관리가 복잡함 |
| 설정 전체를 JSON 컬럼에 저장 | 스키마 변경이 쉽고 쓰기가 단순함 | 참조 무결성, 검색, 집계, 조인이 어려움 |
| 모든 자유 입력을 AI가 자동 저장 | 사용자 입력 단계가 짧음 | 오분류가 알레르기 안전성과 추천에 직접 영향을 줌 |
| 모든 설정을 자유 텍스트로 저장 | 초기 마스터 데이터 구축 비용이 적음 | 정확한 필터링과 일관된 분석이 어려움 |

현재 설정 규모에서는 전체 교체가 단순하고 안전하다. 설정 수가 크게 늘거나 수정 충돌이 중요해지면 증분 갱신과 버전 관리가 필요하다.

### 4.5 추후 구현 및 주의점

- 자유 텍스트 알레르기는 표준 알레르기 ID와 동일한 수준의 안전성을 보장하기 어렵다.
- 설정 전체 교체 시 동시 수정 손실을 막으려면 버전 필드나 조건부 갱신을 검토할 수 있다.
- AI 추출 실패, 낮은 신뢰도, 동의어 처리 정책을 응답에 더 명확히 표현할 필요가 있다.

## 5. 메뉴·카테고리·알레르기 마스터 도메인

### 5.1 책임

이 도메인은 추천과 사용자 설정의 기준이 되는 메뉴, 카테고리, 표준 알레르기 데이터를 관리한다. 메뉴와 알레르기의 연결 정보는 추천 전 안전 필터의 근거가 된다.

### 5.2 중요한 구현과 결정 이유

표준 알레르기는 AI 판단에만 의존하지 않고 DB 관계를 이용해 결정적으로 제외한다. 메뉴·카테고리·알레르기를 별도 마스터로 둔 이유는 다음과 같다.

- 같은 개념을 모든 사용자가 동일한 ID로 참조할 수 있다.
- 추천 전에 안전하지 않은 후보를 SQL 또는 도메인 필터로 제거할 수 있다.
- 카테고리 다양성, 선호도 점수, 이력 집계를 안정적으로 계산할 수 있다.
- 외부 AI가 반환한 문자열을 실제 메뉴 ID 목록으로 제한할 수 있다.

### 5.3 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| AI가 메뉴와 알레르기를 매번 판정 | 데이터 구축이 빠르고 유연함 | 결과가 비결정적이며 안전 경계로 쓰기 어려움 |
| 외부 음식 분류 API 사용 | 넓은 데이터 범위를 빠르게 확보 가능 | 공급자 비용·장애·분류 체계에 종속됨 |
| JSON 문서형 마스터 | 속성 추가가 쉬움 | 관계 검색과 무결성 관리가 어려움 |

안전에 직접 연결되는 표준 알레르기는 결정적 데이터로 유지하고, AI는 추천 순서와 자유 텍스트 보완에 제한적으로 사용하는 것이 현재 설계의 핵심이다.

### 5.4 추후 구현 및 주의점

- 마스터 데이터의 누락은 필터링 누락으로 이어질 수 있으므로 데이터 검수 절차가 필요하다.
- 메뉴와 알레르기 연결의 출처, 검증일, 변경 이력을 관리하는 기능은 추후 구현 대상이다.
- 공개 목록 조회 API가 제품 요구사항에 필요한지는 별도로 확정해야 한다.

## 6. 그룹 도메인

### 6.1 책임

그룹 도메인은 식사 그룹 생성, 구성원 가입과 재가입, 방장 권한, 그룹 음식 설정, 사용자가 참여한 그룹 목록과 상세 조회를 책임진다.

### 6.2 중요한 구현

그룹을 생성할 때 그룹 행과 방장 멤버십을 함께 만든다. 권한 판단은 단순히 그룹의 `ownerUserId`만 비교하지 않고 활성 `group_member`의 역할과 상태를 기준으로 확인한다.

가입 로직은 다음 경우를 구분한다.

- 처음 가입하는 사용자: 활성 멤버로 추가
- 이전에 자진 탈퇴한 사용자: 기존 멤버십을 활성 상태로 복구
- 강퇴된 사용자: 재가입 차단
- 정원 초과: 가입 차단

목록 조회는 사용자가 현재 활성 멤버인 그룹만 페이지 단위로 반환한다. 그룹 상세 조회에서는 그룹 미존재와 멤버 권한 없음이 구분된다.

### 6.3 이 방식을 선택한 이유

- 그룹 소유자 ID만 권한 기준으로 사용하면 멤버 상태와 역할 정보가 서로 어긋날 수 있다.
- `group_member`를 참여와 역할의 기준으로 삼으면 방장도 하나의 활성 멤버라는 규칙을 일관되게 적용할 수 있다.
- 탈퇴와 강퇴를 삭제가 아닌 상태로 구분하면 재가입 정책과 감사 가능성을 유지할 수 있다.
- 가입과 정원 검사를 저장소의 원자적 처리로 묶어 동시에 여러 사용자가 가입할 때 정원 초과 가능성을 줄인다.
- 그룹 수가 계속 늘 수 있으므로 목록은 처음부터 페이지 조회를 사용한다.

### 6.4 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| `ownerUserId`만으로 방장 확인 | 구현이 간단함 | 멤버 역할·상태와 불일치할 수 있음 |
| 탈퇴 시 멤버 행 삭제 | 조회가 단순함 | 재가입·강퇴 구분과 이력 보존이 어려움 |
| 서비스에서 인원 수 조회 후 INSERT | 이해하기 쉬움 | 동시 가입 시 경쟁 조건이 생길 수 있음 |
| 모든 그룹을 한 번에 반환 | API가 단순함 | 데이터 증가 시 응답 크기와 쿼리 비용이 커짐 |

### 6.5 추후 구현 및 주의점

- 방장 양도, 강퇴, 탈퇴 후 그룹 소유권 처리 정책은 별도 요구사항이 필요하다.
- 정원 변경과 가입이 동시에 발생할 때의 잠금 정책을 통합 테스트로 보강해야 한다.
- 테스트 픽스처는 그룹의 소유 사용자 행을 먼저 생성해 외래 키를 만족하도록 정리해야 한다.

## 7. 초대 도메인

### 7.1 책임

초대 도메인은 방장이 단기 초대 코드를 만들고, 사용자가 초대 정보를 확인한 뒤 그룹에 가입하도록 연결한다.

### 7.2 중요한 구현

- 초대 코드는 Redis에 1시간 TTL로 저장한다.
- 무작위 6자리 코드가 이미 존재하면 다시 생성하며 최대 5회 시도한다.
- 코드는 `SETNX` 성격의 원자적 저장으로 충돌을 방지한다.
- 생성 시점에 그룹 존재, 활성 방장 권한, 정원을 검사한다.
- 초대 정보 조회에서는 현재 정원을 기준으로 가입 가능 여부를 함께 반환한다.
- 실제 가입 시점에는 그룹 서비스의 원자적 가입 로직에서 정원과 멤버 상태를 다시 검증한다.

### 7.3 이 방식을 선택한 이유

- 초대 코드는 짧은 수명의 임시 데이터이므로 만료 처리가 자연스러운 Redis가 적합하다.
- 짧은 코드는 사람이 공유하기 쉽지만 충돌 가능성이 있으므로 생성과 저장을 원자적으로 묶어야 한다.
- 조회 시 가입 가능하더라도 실제 가입 전 다른 사용자가 들어올 수 있으므로 최종 검증은 가입 트랜잭션에서 다시 수행해야 한다.
- 초대 도메인이 직접 멤버십을 수정하지 않고 그룹 서비스에 위임하면 탈퇴·강퇴·정원 정책이 한 곳에 유지된다.

### 7.4 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| DB 초대 테이블 | 감사와 관리 화면 구현이 쉬움 | 단기 코드 만료와 정리 비용이 추가됨 |
| 서명된 JWT 초대 링크 | 서버 저장 없이 검증 가능 | 강제 폐기, 사용 횟수, 짧은 사람용 코드 구현이 어려움 |
| 그룹별 영구 초대 코드 | 공유가 편함 | 유출 시 장기간 악용될 수 있음 |
| UUID 전체를 초대 코드로 사용 | 충돌 가능성이 매우 낮음 | 사용자가 직접 입력하거나 전달하기 불편함 |

### 7.5 추후 구현 및 주의점

- 코드 발급 횟수 제한, 가입 시도 제한, 코드 강제 폐기는 추후 구현 대상이다.
- 현재 6자리 공간과 재시도 횟수가 실제 동시 사용자 규모에 충분한지 운영 지표로 확인해야 한다.
- 초대 링크가 외부에 노출됐을 때 방장이 즉시 무효화할 수 있는 기능을 검토할 수 있다.

## 8. 투표 세션 도메인

### 8.1 책임

투표 세션은 추천부터 식당 선택까지 이어지는 전체 업무 흐름의 상태와 시작·종료 시간을 관리한다.

대표적인 상태 흐름은 다음과 같다.

```text
PREFERENCE_INPUT
→ MENU_RECOMMENDING
→ MENU_VOTING
→ MENU_SELECTION 또는 FINAL_MENU_VOTING
→ RESTAURANT_SEARCHING
→ RESTAURANT_SELECTION
→ COMPLETED
```

### 8.2 중요한 구현

- 허용된 상태 전이는 도메인 상태 모델에서 검증한다.
- 비동기 처리나 마감처럼 중복 실행 위험이 큰 변경은 세션을 `findByIdForUpdate` 방식으로 잠근 뒤 현재 상태를 다시 확인한다.
- 시작 시각을 DB에 저장해 서버 재시작 후에도 만료 대상 세션을 다시 찾을 수 있다.
- 만료 처리는 기준 시각과 한 번에 처리할 개수로 조회한다.
- 완료 시 `COMPLETED` 상태와 종료 시각을 함께 기록한다.

### 8.3 이 방식을 선택한 이유

- 상태 전이를 한곳에서 제한하면 서비스마다 서로 다른 순서를 허용하는 문제를 막을 수 있다.
- 스케줄러, 수동 마감, MQ 소비자가 같은 세션을 동시에 처리할 수 있으므로 최종 변경 직전에 잠금과 상태 재검증이 필요하다.
- 만료 시각을 프로세스 메모리나 단기 Redis 키에만 두면 서버 재시작 시 작업을 잃을 수 있다.
- 명시적인 상태 값은 클라이언트 현재 화면, 허용 API, 복구 흐름을 판단하는 기준이 된다.

### 8.4 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| 워크플로 엔진 | 복잡한 분기·재시도·시각화에 강함 | 현재 규모에는 운영과 학습 비용이 큼 |
| Redis TTL 이벤트만 사용 | 만료 처리가 빠르고 단순함 | 만료 이벤트 유실과 재시작 복구가 어려움 |
| 낙관적 락과 재시도 | 잠금 대기가 적음 | 충돌 처리와 재시도 설계가 복잡함 |
| 상태 검증을 각 서비스에 분산 | 초기 구현이 빠름 | 허용 전이가 서로 달라질 위험이 큼 |

### 8.5 현재 한계와 추후 구현

- 수동 세션 생성은 현재 서비스 코드상 그룹 멤버 여부를 확인하지만 방장만 가능하도록 강제하는 검증은 확인되지 않는다. 요구사항이 방장 전용이라면 추후 보완해야 한다.
- 세션 취소·삭제의 방장 권한 검증은 TODO로 남아 있으므로 완료 기능으로 문서화하면 안 된다.
- 상태 전이 실패 후 재시도 정책과 관리자 복구 수단이 필요하다.

## 9. 메뉴 추천 도메인

### 9.1 책임

추천 도메인은 그룹 구성원의 알레르기와 음식 설정, 당일 선호·비선호 키워드, 과거 노출 이력, 메뉴 인기도를 조합해 투표에 사용할 후보를 만든다.

### 9.2 중요한 구현 흐름

```text
방장이 추천 시작 요청
→ 현재 세션과 방장 권한 검증
→ PREFERENCE_INPUT에서 MENU_RECOMMENDING으로 전이
→ 커밋 후 추천 요청 이벤트 발행
→ MQ 소비자가 후보 풀 조회
→ 표준 알레르기 결정적 제외
→ 사용자 선호·비선호와 이력 기반 점수 계산
→ 자유 텍스트 알레르기 후보를 이름 기준으로 추가 제외
→ AI가 안전 후보 안에서 순서와 구성을 조정
→ AI 결과를 실제 후보 ID로 화이트리스트 검증
→ 결과가 비면 결정적 추천 결과로 폴백
→ 후보 저장 후 MENU_VOTING으로 전이
```

후보 풀은 최대 250개 범위에서 만들고 최종 후보는 10개를 목표로 한다. 같은 세션에서 재추천할 때는 이전에 보여준 후보를 제외한다. 특정 카테고리에 결과가 몰리지 않도록 우선 카테고리당 최대 3개를 담고, 부족한 수는 남은 상위 후보로 채운다.

방장이 입력한 당일 키워드는 일반 구성원 신호보다 앞에 `오늘의 핵심 선호`, `오늘의 핵심 비선호`라는 의미를 부여해 AI 프롬프트에 전달한다.

### 9.3 이 방식을 선택한 이유

- 알레르기는 안전 문제이므로 비결정적인 AI가 단독으로 판단하게 하지 않는다.
- 규칙 기반 점수는 재현 가능하고 장애 시 폴백으로 사용할 수 있다.
- AI는 구조화되지 않은 자유 텍스트와 여러 선호 신호를 조합하고 결과 구성을 자연스럽게 만드는 데 사용한다.
- AI가 존재하지 않는 메뉴나 안전 필터 밖의 메뉴를 반환할 수 있으므로 입력 후보와 정확히 일치하는 결과만 허용한다.
- 당일 선호는 장기 프로필보다 현재 식사 의도를 더 강하게 표현하므로 우선순위를 높였다.
- 카테고리 다양성은 상위 점수 메뉴가 한 종류로 편중되어 사용자가 선택할 의미가 줄어드는 문제를 완화한다.

### 9.4 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| 순수 규칙 기반 추천 | 결과가 빠르고 설명 가능하며 비용이 낮음 | 자유 텍스트와 복합 취향 반영이 제한적임 |
| 순수 생성형 AI 추천 | 유연하고 자연스러운 결과를 만들기 쉬움 | 안전성, 재현성, 비용, 존재하지 않는 메뉴 문제가 있음 |
| 임베딩·학습 랭킹 모델 | 대규모 행동 데이터에서 개인화 성능을 높일 수 있음 | 충분한 학습 데이터와 운영 파이프라인이 필요함 |
| 무작위 후보 추출 | 구현이 매우 단순함 | 알레르기와 선호, 추천 품질을 보장하기 어려움 |

현재 방식은 결정적 안전 필터를 바깥 경계로 두고 AI를 그 안의 재정렬 도구로 사용하는 혼합 구조다.

### 9.5 추후 구현 및 주의점

- 자유 텍스트 알레르기의 이름 포함 필터는 동의어, 복합 재료, 오탈자를 완전하게 처리하지 못한다.
- 추천 이유와 제외 이유를 사용자에게 설명하는 기능은 추후 구현 대상이다.
- AI 품질과 비용을 평가할 오프라인 지표, 프롬프트 버전 관리, 실패율 관측이 필요하다.
- 추천 이벤트 발행의 유실을 막기 위한 아웃박스가 필요하다.

## 10. 1차 메뉴 투표 도메인

### 10.1 책임

1차 메뉴 투표는 사용자가 각 후보에 `GO`, `MAYBE`, `NO` 의사를 표시하고, 마감 시 집계 결과로 최종 후보를 결정한다.

### 10.2 중요한 구현

개별 투표와 실시간 집계는 Redis에 저장한다. Lua 스크립트로 다음 작업을 원자적으로 처리한다.

- 신규 투표 제출
- 기존 선택 변경
- 선택별 집계 증감
- 마감 시각 확인
- 투표 닫기와 최종 스냅샷 생성

마감은 스케줄러와 수동 요청이 같은 종료 서비스를 사용한다. 서비스는 DB의 투표 세션을 잠그고 상태를 재검증한 뒤 Redis를 닫아 집계 스냅샷을 얻는다. 스냅샷의 후보가 현재 DB 후보 집합과 일치하는지 검증하고 정책을 적용해 최종 후보와 집계를 DB에 저장한다.

DB 커밋이 끝난 뒤 WebSocket/MQ 이벤트를 발행하고 Redis 임시 투표 데이터를 정리한다. 개인별 1차 선택은 영구 저장하지 않고 최종 집계와 결과만 DB에 남긴다.

후보 수에 따른 흐름은 다음과 같다.

| 최종 후보 수 | 다음 단계 |
|---:|---|
| 0개 | `MENU_SELECTION`에서 방장이 같은 세션 재추천 여부를 결정 |
| 1개 | 해당 메뉴를 바로 최종 메뉴로 확정 |
| 2개 | `FINAL_MENU_VOTING`으로 이동 |
| 3개 이상 | `MENU_SELECTION`에서 방장이 선택 |

### 10.3 이 방식을 선택한 이유

- 투표 변경이 잦고 실시간 집계가 필요해 Redis가 DB 행을 반복 갱신하는 방식보다 적합하다.
- Lua는 사용자 선택 변경과 집계 증감을 하나의 원자적 연산으로 처리해 카운트 불일치를 방지한다.
- 세션 행 잠금과 상태 재검증은 수동 마감과 자동 마감이 동시에 실행돼도 한 번만 결과를 확정하게 한다.
- Redis 정리를 DB 커밋 후에 수행하면 DB 저장 실패 시 원본 투표 스냅샷을 보존할 수 있다.
- 개인표를 영구 저장하지 않으면 개인정보와 저장량을 줄일 수 있고, 제품에 필요한 최종 결과에는 집계만으로 충분하다.

### 10.4 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| 개인 투표를 DB 행으로 저장 | 감사, 재집계, 분석이 쉬움 | 빈번한 변경과 집계 부하가 커질 수 있음 |
| Kafka 이벤트 소싱 | 모든 투표 이력을 보존하고 재생 가능 | 현재 규모에는 운영 복잡도가 큼 |
| 클라이언트가 집계 계산 | 서버 구현이 단순함 | 조작과 불일치에 취약해 신뢰할 수 없음 |
| 낙관적 CAS 반복 | Lua 없이 구현 가능 | 충돌이 많을 때 재시도 비용과 코드 복잡도가 증가함 |

### 10.5 추후 구현 및 주의점

- Redis 장애나 키 유실 시 개인표를 복구할 수 없다. 운영 요구에 따라 DB 감사 로그 여부를 결정해야 한다.
- 무응답자를 분모에 포함하는 방식과 후보 결정 기준은 제품 정책으로 버전 관리할 필요가 있다.
- 0개 후보 재추천을 무제한 허용할지, 이력을 언제 초기화할지 정책이 필요하다.

## 11. 최종 메뉴 결정 도메인

### 11.1 책임

최종 메뉴 도메인은 1차 투표 결과 후보 수에 따라 자동 확정, 2개 후보 최종 투표, 방장 직접 선택을 처리한다.

### 11.2 중요한 구현

- 후보가 1개면 해당 메뉴를 자동 선택한다.
- 후보가 2개면 Redis에 별도의 최종 투표를 열고, 시작 시점의 투표 가능 인원 수를 스냅샷으로 저장한다.
- 후보가 3개 이상이면 방장이 DB에 저장된 최종 후보 중 하나를 선택한다.
- 2개 후보 투표가 동률이면 방장이 최종 선택한다.
- 메뉴 확정은 세션 잠금, 후보 검증, 선택 결과 저장, 상태 전이를 하나의 DB 트랜잭션으로 처리한다.
- 선택 결과에는 중복 최종 선택을 막는 DB 제약을 둔다.
- 커밋 후 임시 Redis 데이터 정리와 다음 단계 이벤트 발행을 수행한다.
- 최종 투표 Redis 데이터에는 2시간 TTL이 있고 만료 세션을 처리하는 스케줄러가 있다.

### 11.3 이 방식을 선택한 이유

- 후보가 하나뿐일 때 추가 상호작용은 의미가 없으므로 자동 확정한다.
- 2개 후보는 구성원의 최종 의사를 다시 묻기 좋은 범위이며, Redis 원자 연산을 재사용할 수 있다.
- 후보가 많을 때 또 한 번 장시간 투표하면 전체 흐름이 지연되므로 방장에게 최종 조정 권한을 준다.
- 동률은 임의 규칙보다 그룹 책임자인 방장이 해결하도록 해 결과에 대한 설명 가능성을 높인다.
- 최종 선택은 이후 식당 검색과 이력의 기준이므로 반드시 DB에 영구 저장한다.

### 11.4 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| 모든 경우 방장이 선택 | 가장 단순하고 빠름 | 구성원 투표의 영향력이 약해짐 |
| 모든 후보로 2차 투표 | 민주적인 결과를 얻기 쉬움 | 후보가 많을수록 결정 시간이 길고 표가 분산됨 |
| 동률 시 무작위·점수순 선택 | 자동 완료 가능 | 사용자가 결과를 납득하기 어려울 수 있음 |
| 최종 개인표도 DB 저장 | 감사와 분석이 가능 | 저장 범위와 개인정보 고려가 늘어남 |

### 11.5 추후 구현 및 주의점

- Redis TTL이 먼저 만료된 경우의 복구와 사용자 안내를 보강해야 한다.
- 최종 투표 중 그룹 멤버 변경 시 최초 스냅샷 인원과 현재 인원의 차이를 어떻게 처리할지 정책이 필요하다.
- 4개 이상 후보도 방장 선택으로 처리하는 현재 정책이 실제 사용자 경험에 적합한지 검증해야 한다.

## 12. 식당 검색 및 선택 도메인

### 12.1 책임

식당 도메인은 최종 메뉴 주변의 외부 장소를 검색해 후보로 저장하고, 구성원이 결과를 조회하며, 방장이 최종 식당을 선택해 세션을 완료하도록 한다.

### 12.2 중요한 구현

식당 검색 요청은 API 요청 안에서 방장 권한과 세션 상태를 먼저 검증한 뒤 비동기 이벤트를 발행한다. 실제 Kakao 장소 검색은 MQ 소비자가 수행한다.

소비자는 다음 순서로 처리한다.

1. 세션을 잠금 조회한다.
2. 여전히 `RESTAURANT_SEARCHING` 상태인지 다시 확인한다.
3. 외부 장소 검색 포트를 호출한다.
4. 결과가 비어 있으면 상태를 바꾸지 않아 재시도 가능하게 둔다.
5. 결과를 저장한다.
6. 세션을 `RESTAURANT_SELECTION`으로 전이한다.

목록 조회는 요청한 그룹과 세션의 관계, 활성 그룹 멤버 여부, 현재 상태를 검증하고 거리순으로 결과를 반환한다. 최종 선택은 방장만 가능하며, 저장된 외부 장소 ID인지 확인한 뒤 세션 완료와 종료 시각 기록을 같은 트랜잭션에서 수행한다.

### 12.3 이 방식을 선택한 이유

- 외부 API 지연이나 일시 장애가 HTTP 요청 시간을 직접 늘리지 않도록 검색을 비동기로 분리했다.
- 권한 검증을 MQ 소비자에게만 맡기면 사용자는 요청 성공 응답을 받은 뒤 내부적으로 실패한 사실을 알기 어렵다. 따라서 요청 시 빠르게 검증하고, 실제 처리 직전에도 상태를 다시 검증한다.
- 외부 검색 결과가 비었다고 세션을 다음 상태로 넘기면 사용자가 선택할 수 없는 상태가 되므로 현재 상태를 유지한다.
- 최종 식당과 세션 완료를 한 트랜잭션으로 묶어 “식당은 선택됐지만 세션은 미완료” 같은 중간 상태를 막는다.

### 12.4 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| HTTP 요청에서 동기 검색 | 구현과 오류 전달이 단순함 | 외부 API 지연·장애가 사용자 요청에 직접 전파됨 |
| 주기적 DB 작업 테이블 폴링 | MQ 없이 재시도와 상태 확인 가능 | 폴링 지연과 작업 테이블 운영 비용이 생김 |
| 검색 결과를 저장하지 않고 매번 호출 | 데이터가 항상 최신일 수 있음 | 비용, 지연, 결과 변동으로 선택 일관성이 낮아짐 |
| 클라이언트가 Kakao API 직접 호출 | 서버 부하가 줄 수 있음 | API 키 노출, 결과 검증, 이력 저장이 어려움 |

### 12.5 추후 구현 및 주의점

- 좌표를 클라이언트 입력으로 받을지 그룹의 저장 좌표만 사용할지 제품·보안 정책을 확정해야 한다.
- 외부 API 재시도, 지수 백오프, 서킷 브레이커, 중복 결과 제거 정책이 필요하다.
- 검색 이벤트의 영속성과 처리 상태를 조회할 API 또는 아웃박스가 필요하다.

## 13. 지난 기록 도메인

### 13.1 책임

지난 기록은 사용자가 접근 가능한 완료 세션을 날짜별로 조회하고, 최종 식당과 메뉴 후보별 집계 결과를 다시 볼 수 있게 한다.

### 13.2 중요한 구현

- 사용자가 현재 활성 멤버인 그룹의 완료 세션만 조회한다.
- 그룹, 세션, 최종 식당, 후보별 최종 집계를 조합해 응답 DTO를 만든다.
- 메뉴 후보 상세는 QueryDSL로 표시 순서와 ID 기준의 안정적인 순서를 보장한다.
- 별도의 캘린더 복제 테이블을 두지 않고 완료된 세션과 연결 데이터를 조회해 기록을 재구성한다.

### 13.3 이 방식을 선택한 이유

- 완료 세션 자체가 식사 결정의 원본이므로 같은 정보를 별도 캘린더 테이블에 중복 저장하지 않아도 된다.
- 활성 그룹 멤버 조건을 조회에 포함하면 사용자가 관계없는 그룹 기록을 보는 것을 막는다.
- 후보와 집계까지 함께 제공하면 결과 메뉴만 보여주는 것보다 결정 과정을 설명할 수 있다.
- 정렬 조건을 명시하면 페이지나 반복 조회에서 결과 순서가 흔들리지 않는다.

### 13.4 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| 완료 시점에 이력 스냅샷 저장 | 조회가 빠르고 당시 상태를 그대로 보존 | 데이터 중복과 동기화 코드가 필요함 |
| 이벤트 소싱으로 기록 재생 | 모든 변경 과정을 재구성 가능 | 저장·조회·운영 복잡도가 큼 |
| 별도 캘린더 테이블 | 캘린더 조회에 최적화 가능 | 원본 세션과 불일치할 위험이 있음 |

### 13.5 추후 구현 및 주의점

- 그룹에서 탈퇴한 사용자의 과거 기록 접근 권한을 유지할지 현재처럼 차단할지 정책 확인이 필요하다.
- 메뉴명이나 식당 정보가 나중에 수정되더라도 당시 값을 보존해야 한다면 완료 시점 스냅샷이 필요하다.
- 기간이 길어질 경우 커서 페이지네이션, 월별 인덱스, 응답 집계 최적화를 검토해야 한다.

## 14. WebSocket 실시간 동기화 영역

### 14.1 책임

WebSocket 영역은 투표 세션 상태 변경과 집계 변경을 구독 중인 클라이언트에 빠르게 알린다. 영구 상태의 원본은 WebSocket이 아니라 DB와 Redis이며, REST 현재 상태 API가 복구 경로를 제공한다.

### 14.2 중요한 구현

- `/ws` STOMP 연결을 제공한다.
- `CONNECT` 시 JWT 서명, 만료, 블랙리스트, 사용자 상태를 검증한다.
- `SUBSCRIBE` 시 `/topic/vote-sessions/{sessionId}` 경로 형식과 해당 그룹의 활성 멤버 여부를 검증한다.
- 클라이언트의 임의 `SEND`는 차단하고 서버가 상태 이벤트만 발행한다.
- 연결이 끊기거나 이벤트를 놓친 클라이언트는 현재 상태 REST API로 전체 상태를 다시 받는다.

### 14.3 이 방식을 선택한 이유

- 연결 인증만 검사하고 구독 권한을 검사하지 않으면 로그인 사용자가 다른 세션 ID를 추측해 이벤트를 볼 수 있다.
- 클라이언트 SEND를 막으면 실시간 채널을 서버 상태 알림 전용으로 유지하고 조작 표면을 줄일 수 있다.
- WebSocket 이벤트는 영구 로그가 아니므로 재연결 시 누락될 수 있다. REST 스냅샷을 진실의 원천으로 두면 복구가 가능하다.
- STOMP는 목적지 기반 구독과 Spring 연동이 단순해 현재 요구사항에 적합하다.

### 14.4 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| 주기적 REST 폴링 | 구현과 인프라가 단순함 | 지연과 불필요한 요청이 증가함 |
| SSE | 서버 단방향 알림에 단순하고 HTTP 친화적임 | STOMP 목적지와 양방향 확장성은 제한적임 |
| 외부 브로커 릴레이 | 다중 인스턴스에서 확장과 전달 안정성이 좋음 | 별도 브로커 운영이 필요함 |
| WebSocket 이벤트만으로 화면 상태 구성 | 빠르고 증분 갱신에 적합 | 이벤트 누락 시 상태가 틀어짐 |

### 14.5 추후 구현 및 주의점

- 현재 단순 브로커는 다중 서버 인스턴스 간 구독 전달을 보장하지 않는다. 운영 확장 시 외부 브로커 릴레이가 필요하다.
- 재연결 백오프, 마지막 이벤트 버전, 중복 이벤트 처리 규칙을 프런트와 합의해야 한다.
- 인증 만료 후 유지 중인 연결을 언제 종료할지 정책을 명확히 해야 한다.

## 15. MQ 및 비동기 이벤트 영역

### 15.1 책임

MQ 영역은 추천 생성, 식당 검색, 투표 결과 후속 처리처럼 요청 응답과 분리할 수 있는 작업을 이벤트로 연결한다.

### 15.2 중요한 구현

- 이벤트는 공통 `EventEnvelope` 형태로 전달한다.
- RabbitMQ 토픽 교환기를 사용해 이벤트 종류별 라우팅을 구성한다.
- 소비자는 메시지 식별자를 바탕으로 중복 처리 방지 구조를 사용한다.
- 추천과 식당 검색 소비자는 메시지 수신 후 현재 DB 상태를 다시 확인하고 핵심 작업을 수행한다.
- 다음 이벤트는 가능한 한 DB 커밋 이후 발행한다.
- JSON 역직렬화 신뢰 패키지를 `com.gm.mq.event` 범위로 제한한다.

### 15.3 이 방식을 선택한 이유

- OpenAI와 Kakao 같은 외부 연동은 지연과 실패 가능성이 있어 HTTP 트랜잭션과 분리하는 편이 사용자 응답성과 재시도에 유리하다.
- 메시지는 중복 전달될 수 있으므로 소비자가 멱등성을 갖거나 중복을 식별해야 한다.
- 소비 시 현재 상태를 다시 확인하면 오래된 이벤트가 이미 진행된 세션을 되돌리는 것을 막는다.
- 역직렬화 가능한 타입 범위를 제한하면 임의 클래스 역직렬화 위험을 줄일 수 있다.

### 15.4 다른 방식과 비교

| 대안 | 장점 | 단점 |
|---|---|---|
| 서비스 간 동기 호출 | 흐름과 오류 전파가 단순함 | 외부 지연과 장애가 요청에 직접 연결됨 |
| Spring 인프로세스 이벤트 | 설정이 간단하고 빠름 | 프로세스 종료 시 유실되며 서버 간 전달이 안 됨 |
| Kafka | 대규모 스트림과 재생에 강함 | 현재 이벤트 규모에는 운영 부담이 클 수 있음 |
| DB 아웃박스 + 릴레이 | DB 변경과 발행 의도를 원자적으로 기록 | 추가 테이블, 릴레이, 정리 운영이 필요함 |

### 15.5 추후 구현 및 주의점

- DB 커밋 직후 프로세스가 종료되면 이벤트가 발행되지 않을 가능성을 제거하려면 트랜잭셔널 아웃박스를 구현해야 한다.
- 투표 결과 후속 처리와 알림·SOLAPI 소비자 일부는 TODO이므로 현재 완성 기능 범위에서 제외해야 한다.
- DLQ 재처리 도구, 최대 재시도 횟수, 독성 메시지 격리, 운영 알림이 필요하다.

## 16. 도메인 간 핵심 데이터 흐름

```text
인증
  └─ 사용자 생성/활성화
       └─ 음식 설정 및 알레르기
            └─ 그룹 생성/가입
                 └─ 투표 세션 생성
                      └─ 메뉴 추천
                           └─ 1차 메뉴 투표
                                └─ 최종 메뉴 결정
                                     └─ 식당 검색/선택
                                          └─ 세션 완료
                                               └─ 지난 기록 조회
```

이 흐름에서 중요한 경계는 다음과 같다.

| 경계 | 진실의 원천 | 일시 데이터 | 주요 동시성 보호 |
|---|---|---|---|
| 인증 | 사용자 DB, Refresh Token 저장 | Login Exchange, Access Token 블랙리스트 | 일회용 코드 원자 소비 |
| 그룹 | 그룹·멤버 DB | 초대 코드 | 원자 가입과 정원 검사 |
| 추천 | 세션·후보 DB | MQ 메시지 | 세션 잠금과 상태 재검증 |
| 1차 투표 | 확정 결과 DB | 개인표·실시간 집계 Redis | Lua 원자 연산과 세션 잠금 |
| 최종 메뉴 | 최종 선택 DB | 2개 후보 최종표 Redis | DB 유일성 제약과 세션 잠금 |
| 식당 | 검색 결과·선택 DB | MQ 메시지 | 세션 잠금과 상태 재검증 |
| 실시간 알림 | DB·Redis 상태 | WebSocket 이벤트 | 구독 권한 검증, REST 재동기화 |

## 17. 전체 설계 결정 요약

현재 백엔드는 모든 데이터를 한 저장소와 한 처리 방식으로 통일하기보다 데이터 성격에 따라 역할을 나눈다.

- 장기 보존과 업무의 최종 결과는 DB에 저장한다.
- 짧은 수명과 높은 변경 빈도를 가진 인증 교환 정보와 개인 투표는 Redis에 저장한다.
- 외부 API처럼 느리고 실패할 수 있는 작업은 MQ로 분리한다.
- 사용자에게 즉시 알려야 하는 변화는 WebSocket으로 전달하되, REST 상태 조회를 복구 수단으로 둔다.
- 알레르기처럼 안전에 연결되는 규칙은 결정적으로 처리하고, AI는 안전 후보 안의 정렬과 자유 텍스트 보완에 사용한다.
- 중복 실행 위험이 있는 세션 전이는 DB 잠금과 현재 상태 재검증으로 직렬화한다.

이 설계는 현재 제품 규모에서 구현 복잡도를 통제하면서도 투표와 비동기 처리의 핵심 경쟁 조건을 방어하려는 선택이다. 반면 아웃박스, 다중 인스턴스 WebSocket 브로커, 운영 재처리 도구, 토큰 회전, 완전한 회귀 테스트 복구는 운영 수준으로 가기 전에 보완해야 할 과제다.
